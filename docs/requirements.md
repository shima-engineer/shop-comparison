## 1. サービスの目的・コンセプト

### 開発目的（与件より ✅）
- 自身が実際に感じた課題（幹事の店選び・共有・意思決定の負担）を解決する
- 実用性のあるWebサービスを公開する
- エンジニアとしての技術力向上、転職用ポートフォリオ、Claude Codeを活用した開発工程の習得

### 開発の制約（与件より ✅）
- 個人開発 / 開発期間1ヶ月以内 / 初期リリースは必要最低限の機能 / 初期・運用費用を最小化 / 過剰設計を避ける

### 開発の優先方針 ✅
- 実用性とポートフォリオ価値を両立する。判断に迷った場合は**ポートフォリオとしての価値を優先**する。
  - 実際に使われた実績（利用データ・フィードバック）もポートフォリオ価値に含める。

### ユーザーヒアリングで得た一次情報 ✅
- 店探し（A）と意思決定（B）は同程度に負担だった。
- 参加者ごとに「昼が良いか／夜が良いか」「昼しか／夜しか行けないか」を個別に聞くのが手間だった。
- LINEの投票機能では店名しか載せられず、参加者に各店を調べてもらう必要があった。
- 禁煙席の有無、コースしか選べないか等の「懸念事項」を調べるのが大変だった。

### コンセプト ✅
> **幹事が候補店を「判断に必要な情報つき」で集め、LINEで共有し、ログイン不要の投票で決めるまでを最短で終えられるサービス**

- 検索（A）と意思決定（B）を同等に扱う。両者をつなぐ中心は「**店舗情報カード**」（予算・禁煙・昼/夜営業・最寄駅・コース等の要点）とし、検索結果と投票ページで同じ情報を見せる。
- 参加者は投票ページだけで比較・判断でき、各店を自分で調べる必要がない。

### スコープ境界
- ✅ 日付の調整・決定は対象外（日程調整サービスとは競合しない）。
- ✅ 時間帯（昼/夜）の希望を投票時に集める（日付は扱わない）
- ✅ 時間帯の回答は**参加者ごとに1回**（5段階：昼しか無理／昼がいい／どちらでも／夜がいい／夜しか無理）。店舗カードには各店の昼/夜営業と照合した「参加できない人数」を表示する。
  - 店舗ごとに時間帯希望が変わるケースはMVP対象外（🟡 少数と仮定）

## 2. ターゲットユーザー ✅

| 区分 | 想定 |
|---|---|
| 主ユーザー（幹事） | 20〜30代。友人・同期などの食事会（**6人前後**、4〜10人程度）で店選びを担う人。連絡手段はLINEグループ |
| 副ユーザー（参加者） | 幹事からLINEでURLを受け取る人。サービスを知らず、登録する動機もない。主にLINEアプリ内ブラウザ（スマホ）で開く。**幹事と親しいとは限らず、グループ内で発言しづらい**ことがある |
| 対象地域 | **東京23区**（MVP） |
| 対象外 | 数十人規模の宴会、接待、予約代行が必要なケース |

**原体験（一次情報）**: 同期6人の集まり。面識の薄い参加者もおり気軽に聞けないことが多かった。LINEグループで発言していたのは幹事ともう1人程度だった。

## 3. ユーザーが抱えている課題 ✅

| # | 課題 | 主体 |
|---|---|---|
| P1 | 条件に合う店を探すのに時間がかかる | 幹事 |
| P2 | 懸念事項（禁煙、コースのみか、昼/夜営業、予算）の確認が大変 | 幹事 |
| P3 | 候補店の情報が各サイトに散らばり比較しづらい | 幹事・参加者 |
| P4 | LINE共有用の文章作成が面倒 | 幹事 |
| P5 | LINE投票には店名しか載せられず、参加者が各店を自分で調べる必要がある | 参加者 |
| P6 | 参加者の時間帯（昼/夜）の都合を個別に聞く手間がある | 幹事 |
| P7 | 参加者がグループで発言しづらく、意見や懸念が集まらない | 幹事・参加者 |
| P8 | 電話でしか空席・予約状況を確認できない店がある | 幹事 |

## 4. サービスが提供する価値 ✅

| 価値 | 対応課題 |
|---|---|
| 条件を入れるだけで、外部APIから候補店を手入力なしで集められる | P1 |
| 懸念事項を「店舗情報カード」で一目で確認でき、APIで判定できない項目は「未確認」と明示される | P2, P3 |
| 投票ページに店舗情報カードが載るため、参加者は自分で調べずに判断できる | P3, P5 |
| LINE共有文と投票URLが自動生成され、コピー or LINE送信するだけ | P4 |
| 時間帯の都合を投票と同時に回収し、店ごとに参加できない人数が分かる | P6 |
| ログイン不要・発言不要で、タップだけで意思表示できる | P7 |
| 予約・空席は解決しない。電話番号・予約ページへの導線と「空席未確認」の明示で**緩和のみ** | P8 |

## 5. 既存サービスとの差別化 🟡（合意待ち）

> 調査日: 2026-11-24。本環境からは各サイトへの直接アクセスができなかったため、Web検索結果（公式サイトの抜粋・紹介記事）に基づく。各サービスの最新仕様は未検証の部分を含む。

### 5.1 既存サービス調査

| サービス | 概要 | 候補店の追加 | 店舗情報の表示 | ログイン | 本サービスとの関係 |
|---|---|---|---|---|---|
| LINE 投票機能 | トーク内で投票作成 | 手入力（画像付き選択肢も可とする記事あり） | 店名・画像程度 | 不要（LINE内） | 課題P5の原因。匿名投票オプションあり [R1][R2] |
| 店決めさん | ブラウザ拡張（Chrome/Edge/Firefox） | 食べログ/ホットペッパーの閲覧中ページからワンクリック追加 | 未確認 | 参加者は不要 | **最も近い競合**。幹事はPC＋拡張機能が前提 [R3][R4] |
| 調整丸（ぐるなび） | 日程調整＋候補店アンケート | ぐるなび掲載店を検索/URLで追加 | ぐるなび店舗情報を回答ページに掲載 | 不要 | 主目的は日程調整。ぐるなび掲載店のみ [R5][R6] |
| 多数決さん / Nanovote / minervameet 等 | 汎用の登録不要投票 | 手入力 | なし | 不要 | 店舗情報なし [R4][R7] |

**事実**: 「候補店を選ぶ → 投票URLを共有 → ログイン不要で投票」という基本フロー自体は既存サービスで実現されている。
**示唆**: 基本フローだけでは差別化にならない。差別化は以下に置く。

### 5.2 差別化ポイント（🟡 仮説）

| # | 差別化 | 既存との違い |
|---|---|---|
| D1 | **懸念事項が分かる店舗情報カード**（禁煙・昼/夜営業・コース・予算。不明項目は「未確認」と明示） | 既存は店名・リンク中心で、参加者は結局リンク先を調べる |
| D2 | **時間帯の都合×営業時間の照合**（店ごとに「行けない人数」を表示） | 調査範囲では同等機能は見当たらない |
| D3 | **遠慮しない投票**（他の参加者に誰が何に投票したか見せない） | LINE投票は匿名設定可だが店舗情報がない |
| D4 | **スマホ完結・条件検索から一気通貫** | 店決めさんはPC拡張機能、調整丸は日程調整が主 |

### 5.3 差別化しない領域
- 店舗検索の網羅性・口コミ・評価（グルメサイトに任せる）
- 日程調整（調整さん・調整丸に任せる）
- 予約・空席確認
